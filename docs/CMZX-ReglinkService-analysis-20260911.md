`0x38`의 다섯 번째 데이터 `A0`에서 `A0 & 08 = 00`이므로, DUDU 기준의 미러 상태 후보는 OFF다. 이는 실제 기능 상태를 아직 검증하지 않은 해석이다. 다른 비트가 그대로인 상태에서 이 비트만 ON으로 바뀌면 다섯 번째 바이트는 A8이 되지만 전체 패킷의 다른 값까지 고정된다고 가정하지 않는다.

실차 버전과 같은 이름의 [Reglink 공개 묶음 26090708](https://reglink-car.oss-cn-shenzhen.aliyuncs.com/scripts/scripts_enc_26090708.zip)을 확보했다. 원본 ZIP은 9,231,418바이트, SHA-256 `db96af09c59da0a2324dc1cf5759ff64e4ed0c5c83ef5f0164c103cc11a17e06`이고 ZIP CRC에 오류가 없었다. 여기서 복호화한 `model_raise_psa.js`는 139,118바이트, SHA-256 `d5d7302e5d4eef766de713240f211647c0195b20bd46d84d54b2561ad2a5ae5d`로 앞서 확보한 26082601·26091003과 동일하다. 해당 서버 파일에도 미러 설정 메뉴가 없다. 차량 내부의 활성 스크립트 파일 바이트를 직접 읽은 것은 아니다.

### 0.3 APK 구현

`CMZX-MirrorCheck-v03.apk`는 기존 0.2와 동일 패키지·서명을 사용하고 versionCode는 3이다. **실차 미러 설정 시험** Activity를 추가했다. 이 화면에서 사용자가 켜기·끄기를 확인하면 `ICANBoxService.write(CANBoxPacket)`을 한 번만 호출하며, 허용된 패킷은 type `0x80`, 데이터 `[0x1E, 0 또는 1]`이다. 실제 설정 명령이므로 0.2의 읽기 전용 범위와 구분한다.

원본 서비스의 `write` 반환형은 void다. 내부에서는 디코더의 `encode`를 거쳐 기존 MCU 통신으로 전달하지만 일시중지·비활성 상태 또는 전달 모드에 따라 송신되지 않을 수 있다. 따라서 ‘예외 없이 반환’은 실제 송신이나 차량 적용 성공을 뜻하지 않게 표시했다.

송신 전에 서비스 해시와 버전, 실차에서 확인된 차종·제품·MCU·CAN·런타임 조건, 9바이트 수신 형식 및 OFF/ON 인코더 결과를 검사한다. 5초 이내의 한 번만 사용할 수 있는 요청으로 중복·만료·송신 전 취소를 제한한다. 임의 패킷 입력, rawWrite, 프로필 변경, 스크립트 교체, 자동 반복 송신은 없다. 기존 진단·샘플 화면은 설정을 보내지 않는다.

시험 전 보고서를 앱 내부에 저장하고, 설정 호출 후 8초간 0x38 콜백과 캐시를 관찰한다. 콜백 등록/해제는 서비스 함수 1/2를 사용하며, 추가 CAN 상태 요청 패킷은 보내지 않는다. 캐시는 패킷별 시각이 없고 콜백도 차량 ACK로 단정하지 않는다. 켜기·끄기는 수동 실행이며 앱 종료나 삭제 시 자동 복원하지 않는다.

### 시험 순서

1. 차량 올인원에 v03을 설치하고 **실차 미러 설정 시험 → 1. 차량 연결 확인**을 실행한다.
2. 정차·P단·주차브레이크 상태에서 **2. 미러 하향 켜기 → 켜기 1회 실행**을 선택한다.
3. 약 8초간 관찰이 끝나면 **시험 결과 복사/공유**로 전체 기록을 보낸다.
4. 시동이 켜진 상태에서 브레이크를 유지하고 R단을 선택해 미러가 내려가는지 확인한 뒤 P단으로 돌아온다. 실제 동작 여부도 함께 기록한다.

후진 하향 동작은 [Peugeot 5008 2019 공식 설명서](https://carros.peugeot.com.br/content/dam/peugeot/brazil/b2c/owners/maintain-your-car/manuais/5008/5008-br-manual-capa-garantia-ed19-19.pdf)의 인쇄 89쪽에서 엔진 작동 중 후진 선택 시 작동하는 기능으로 안내한다. 국가·사양별 차이가 있을 수 있으며 사용자는 자신의 차량에서 순정 동작을 확인했던 이력이 있다.

## 결론

**현재 사진과 일치하는 2014~2019 5008 메뉴를 코드로 재현했고, 후진 미러 하향 스위치가 구현되어 있지 않음을 확인했다.** APK 내장 파일뿐 아니라 공개 서버의 `26082601`과 `26091003` 묶음에서도 해당 Raise PSA 메뉴 파일은 바이트까지 동일하다.

**DUDU 성공 코드와 Reglink 코드의 미러 설정 직렬 프레임 계산도 일치했다.** 이는 별도 구현을 진행할 근거다. 실제 차량의 설정 상태, 요청 수락 및 거울 움직임까지 확인된 것은 아니다.

차량 없이 사용할 수 있는 샘플 모드와, 나중에 차량에서 정보를 모을 읽기 기능을 넣은 독립 APK **CMZX-MirrorCheck-v02.apk**를 제작했다. 이 앱은 실제 미러 설정을 변경하지 않는다.

## DUDU 성공 자료와 명령 대조

[개발자 APK 제공 및 사용자 성공 확인 게시물](https://forum.dudu-auto.com/d/2051-missing-function-auto-tilt-down-of-side-mirror-when-reversing)의 대상은 Peugeot 3008 / DUDU / Raise PSA-RZ-15다. 기존 조사에서 해당 게시물의 APK 두 개를 확보했다. 사진의 CAN 박스 전체 버전 문자열은 사용자 차량과 같지만 본체 플랫폼은 다르다.

성공 파일의 미러 스위치를 추적하면 다음으로 연결된다.

- UI: `DataCanbus.DATA[276]`을 읽어 0 또는 1로 토글
- 앱 호출: `PROXY.cmd(88, [30, 값], null, null)`
- 서비스: `carSet(0x1E, 값)`
- FYT MCU 함수 인자: `[E3, 05, 80, 1E, 값]`

추가로 `ToolkitDev.writeMcu`와 `CanbusTypeRZC4.write`를 분석했다. RZC4의 본체 측 분석 경로는 위 인자를 `[E9, FD, 05, 80, 1E, 값, 체크섬]` 형태로 포장한다. 여기의 `E9` 역시 FYT MCU용 접두어다. 해당 경로의 FD 직렬 프레임 부분은 다음과 같다.

| 설정 | DUDU RZC4 코드 계산 | Reglink RaisePsaDecoder 코드 계산 |
|---|---|---|
| OFF | `FD 05 80 1E 00 A3` | `FD 05 80 1E 00 A3` |
| ON | `FD 05 80 1E 01 A4` | `FD 05 80 1E 01 A4` |

Reglink에는 `CANBoxPacket(type=0x80, data=[0x1E, 값])`을 넣은 계산이다. 길이는 데이터 길이+3, 체크섬은 길이·종류·데이터 합계의 하위 8비트다.

이로써 이전에 남겨 두었던 **짧은 두 바이트 데이터 형식의 코드상 대응 관계**를 추가로 검증했다. Reglink의 다른 설정 항목에 있는 후행 0 바이트를 무조건 복사할 필요가 있다고 볼 근거는 없다. 다만 표의 값은 코드 계산값이며 실차 캡처나 실제 송신 성공 기록은 아니다. DUDU 성공 차량이 어느 내부 송신 분기를 사용했는지도 로그로 확인한 것은 아니다.

이 값들은 CAN 박스와 본체 사이의 직렬 프로토콜 형식이다. 차량 CAN 중재 ID와 데이터 프레임으로 취급하면 안 된다.

## 수신 상태 바이트의 대응

DUDU의 RZC4 수신기는 정상 FD 프레임에서 `onHandle(frame, frameStart+1, ...)`을 호출한다. `onHandle`은 그 기준점의 +1에서 종류를, +2부터 데이터 본문을 읽는다. 미러 상태는 기준점 +6의 bit 3을 읽어 데이터 276에 반영한다.

따라서 순수 데이터 기준으로는 **종류 `0x38`, `data[4] & 0x08`**, 즉 다섯 번째 바이트의 bit 3이다. 프레임의 오프셋 +6을 순수 데이터의 `data[6]`으로 옮기면 잘못된 위치를 읽게 된다.

다른 미러 관련 이름을 가진 기존 데이터 194는 같은 바이트의 bit 0이며 이번 성공 토글과 구별해야 한다.

합성 프레임으로 256개 바이트 값을 대조해 두 인덱스 해석의 대응을 검사했다. 이는 계산 검증이며 사용자 차량에서 해당 비트가 실제 설정 상태를 나타낸다는 실측 검증은 아니다.

## 0.2 설치 오류 수정 — Android 16 / One UI 8.5

사용자가 0.1 APK를 설치했을 때 ‘앱이 설치되지 않음’이 표시됐고, 소프트웨어 정보 사진에서 Android 16 / One UI 8.5가 확인됐다. 원본 APK에서는 `resources.arsc`가 DEFLATE 압축되어 있고 데이터 시작 위치가 850바이트(4로 나눈 나머지 2)였다. [Android 공식 설치 조건](https://developer.android.com/about/versions/11/behavior-changes-11#app-packaging)은 targetSdk 30 이상 앱의 리소스 테이블을 비압축·4바이트 정렬 상태로 요구한다. 기존 APK는 targetSdk 33이므로 이 조건을 위반했다. 이전 서명·DEX 검사만으로는 이 패키징 결함을 잡지 못했다.

0.2에서는 AAPT2가 생성한 APK를 다시 압축하지 않고 그대로 보존한 뒤 DEX를 추가한다. 서명 완료 파일의 `resources.arsc`는 비압축이며 데이터 시작 위치는 848바이트로 4바이트 정렬 조건을 충족한다. 빌드에 최종 APK 패키징 검사를 추가했다. 기존 파일의 동일 결함이 검사에서 거부되는 것도 확인했다. 패키지 및 서명 키를 유지하고 versionCode를 2로 올렸다.

Android Build Tools 36.0.0의 [zipalign](https://developer.android.com/tools/zipalign) 및 [apksigner](https://developer.android.com/tools/apksigner) 검사에 통과했다. 서명 검증 범위는 API 21~36이다. 이는 도구에 의한 파일 검사이며, Android 16 기기에서 설치·실행한 결과는 아니다. 사용자의 상세 설치 오류 코드는 없으므로 이 결함 외에 추가 원인이 존재하는지는 미확인이다.
